# models/

Artifacts of trained models and the registry to track their provenance.
Similarly to `data/` and `logs/`, the big binary files in this directory are
not version-controlled; rather, the structure and the registry of which
checkpoint matters and why are version-controlled according to the 
reproducibility pledge in the root `README.md`.

## Layout

```
checkpoints/
  latest/    every checkpoint saved during a training run, in order
  best/      the single best checkpoint per run, by whatever metric
             CheckpointManager.save(is_best=True) was called with
             (see config/training.yaml's checkpointing.keep_best_by_metric)
metadata/
  model_registry.yaml   append-only log of every checkpoint ever
                        saved: run name, step, path, metrics, config
onnx/

Artifacts of trained models and the registry to track their provenance.
Similarly to `data/` and `logs/`, the big binary files in this directory are

## Layout

```
checkpoints/
  latest/    every checkpoint saved during a training run, in order
  best/      the single best checkpoint per run, by whatever metric
             CheckpointManager.save(is_best=True) was called with
             (see config/training.yaml's checkpointing.keep_best_by_metric)
metadata/
  model_registry.yaml   append-only log of every checkpoint ever
                        saved: run name, step, path, metrics, config
onnx/
  exported ONNX policies, produced by scripts/export_onnx.py from a
  checkpoint in checkpoints/best/, and what serving/app/main.py
  actually loads at deployment time
```

## Provenance

Each checkpoint saved using `rl.utils.checkpoints.CheckpointManager.save()`
will have a corresponding record in `metadata/model_registry.yaml` - what
run created it, at what training step, with what metrics, and
(if given) a link to the specific `config/training.yaml` used
when that checkpoint was created. Before believing anything in
`docs/experiments/`, verify it by checking through the registry
back to the checkpoint that created it - a checkpoint without
a registry entry is not the foundation for a reported result.

## Why the binaries aren't committed

The model weights are a large binary artifact that doesn’t really
diff in git. The registry (which is a small and human-readable YAML
file) is the only thing that actually needs to be versioned;
the weights can be regenerated by training on the configuration in
the registry, or just need to be provided separately somehow.
  The ONNX policy exports, generated by running scripts/export_onnx.py
  using a checkpoint found in checkpoints/best/, and what’s loaded
  by serving/app/main.py at runtime
```
